# Business bank, payout and order details

Owners can view masked Stripe bank details and a paged bank-payout history. Bank changes use the existing owner-only Stripe Express login-link action; Cal-Eats does not accept account numbers, sort codes or IBAN input. The API returns only bank name, last four digits, country, currency, verification state and default-currency flag. Full account/routing numbers, holder names and fingerprints are discarded by the provider adapter and the API allow-list. A permission limitation is shown as unavailable bank details, without expanding the restricted key's permissions.

The hosted preview remains `local_simulator`. It therefore shows no connected Stripe bank or actual bank payouts. These views activate against the restaurant's own mode-bound Connect account after Stripe setup is completed. Original Calai live banking is untouched.

## Owner API

- `GET /api/restaurant/restaurants/:restaurantId/finance/stripe/banking`: provider mode/configuration, connection and account readiness, masked `bankAccounts`, `bankDetailsAvailable`, `canManageBankDetails`, weekly schedule, refreshed time and an explanatory note.
- `GET .../finance/stripe/payouts?pageSize=20&startingAfter=po_...`: `items`, `hasMore`, `nextCursor`, provider mode and configured state. A cursor must already belong to that restaurant and connected account. Existing payout IDs cannot be rebound or updated through another restaurant's response.
- Existing `POST .../finance/stripe/dashboard` with an idempotency key creates the owner-only Stripe Express link. The bank-editing operation itself remains on Stripe.
- `GET .../finance/orders/:orderId/breakdown`: immutable order-item/modifier prices and promotion allocation, original/retained commission, commission basis/rate, refunds and reversals, original/current restaurant earnings and transfer state.

Payout `createdAt` comes from Stripe's payout object. `expectedArrivalAt` is the provider's expected arrival (`arrivalAt` remains a compatibility alias). `paidAt` is populated only from a completed, restaurant/account/mode-bound signed `payout.paid` event, not from the expected arrival date or a local refresh timestamp. That event means Stripe expects availability; it does not independently verify the restaurant's bank statement. Failures can be reported after a paid event. A connected-balance transfer or eligible order is not shown as a bank payout, and orders are not attributed to a particular bank payout without reconciliation evidence. Current marketplace payout storage is GBP; an unverified/non-GBP provider response is rejected rather than displayed as pounds.

The order breakdown uses stored checkout and commercial-policy snapshots, never today's menu, offer or contract. Food price before promotion, restaurant-funded discount, charged food/delivery, recorded refunds and commission reversals remain separate. A free item's stored retail value is informational; it is not the restaurant's food cost and is not deducted a second time from earnings. Processing fees remain platform-borne under the current model. Pending/cancelled orders do not show recognised restaurant earnings.

Staff, customers, platform-admin users and other restaurants cannot use these owner routes. Native business bearer sessions use the same authorization path as the tablet portal. Four focused financial-detail tests passed for promotion/free-item/refund arithmetic, snapshot preservation, role/tenant/mode boundaries, bank masking, payout cursors and event-vs-expected dates. The integration case creates real offer campaigns and orders through the APIs, changes the menu, records a later partial refund, and verifies both owner details and original-pricing CSV fields. Four existing weekly-statement checks and twenty affected provider/Connect regressions also passed; an old error-message-only assertion was corrected to check the configuration error type. Tests use isolated databases and fake Stripe responses; no real charge, bank edit, payout, refund or transfer was performed.

Primary provider references: [external bank accounts](https://docs.stripe.com/api/external_account_bank_accounts/list), [payout object](https://docs.stripe.com/api/payouts/object), [payout event meanings](https://docs.stripe.com/api/events/types).

## Client review — 28 October 2026

The tablet/browser portal and separate Cal-Eats Admin native app expose the same owner-only bank, payout and order breakdown APIs. Native bank fields tolerate missing country, currency and last-four values. Staff cannot open the owner finance tools. Order history now uses bounded pages and server-side status filters; a historical deep link loads only the requested restaurant's order.

The final focused customer review fixed startup failures, stale restaurant/menu responses, basket edits lost during refresh, and ambiguous checkout retries. Browser and native checkout now retain the exact original reviewed request and idempotency key after a lost response, including subsequent authentication or throttling failures. Successful order creation followed by a payment-link failure returns customers to their existing order. The browser price checker also has a bounded timeout and explicit retry. Its shared checkout module is explicitly served as JavaScript by the API static allow-list.

Validation passed: the 28 finance/weekly/provider checks above; 12 native customer checks; 25 browser model/offer checks; two shared checkout recovery regressions; and the two focused customer-journey/price-review integrations. Both native apps passed TypeScript and iOS/Android JavaScript bundle exports; the portal production build and repository release checks passed. An actual local browser checkout created one simulated £12.75 collection order and opened its tracking page with no captured browser errors. The saved discounted-order walkthrough showed £12.75 original food, £1.27 restaurant discount, £0.80 commission and £10.68 restaurant earnings. Phone review found and corrected intrinsic grid-width overflow in Earnings.

These checks do not establish zero defects or signed-device/store readiness. Real Stripe banking, payout and payment validation remains gated by the owner's deferred verification; the preview uses simulated payments. Apple currently disables membership benefits while processing the individual-to-organisation migration; Google developer verification was deferred. Physical-device journeys, background push, signing, store submissions and production release gates remain separate required work. Original Calai accounts, live Stripe and tablet management were not changed.
