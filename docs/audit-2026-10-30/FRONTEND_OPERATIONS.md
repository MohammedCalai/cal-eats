# Cal-Eats frontend and operations audit

Audit date: 30 October 2026. Source baseline: `b94092ee4657b01d93466a4ddf282155f76a0fa2`. This document records source inspection and a synthetic backup reproduction. It does not certify a deployed service, signed app, device, or hosting account. No production configuration, application source, database or reference source was changed for this review.

## Assessment

The project has useful separation between customer web, restaurant portal, customer native app, business native app and the API. Shared menu/alert rules, tenant-aware resource views, explicit native credentials, checkout retry state and a deliberately bounded test command are worth retaining. A rewrite is not justified by the evidence.

The main frontend scalability problem is avoidable request amplification; the main operations gaps are backup completeness, recovery packaging and a missing automated release gate. The native apps and portal have meaningful logic tests, but those do not demonstrate interactive screens, background delivery, accessibility or physical-device behaviour. A comprehensive production readiness claim cannot be made from this checkout.

The newer `docs/STRIPE_TEST_TRIAL.md` records a hosted Stripe sandbox trial on 29 October, including two authorizations/captures and refunds. This is historical recorded evidence, superseding older blanket statements that nothing was hosted or tested with Stripe. The trial explicitly does not verify live funds or bank payouts; no fresh provider or deployment verification was performed in this sub-audit.

## Existing safeguards to retain

- Customer DOM rendering generally uses escaping helpers; the receipt test explicitly checks hostile restaurant/item strings (`apps/web/test/customer-ui.test.js:5-8`). No demonstrated DOM injection is asserted by this audit.
- Portal role/navigation checks are complemented by backend authorization. Tenant preference in local storage is revalidated against returned memberships (`App.jsx:123-151`). Stored tenant selection is not authorization.
- Native API clients reject insecure non-loopback API origins and original-Calai hosts, omit cookies, use bearer credentials, reject redirects and impose deadlines. Native session tokens are stored with SecureStore; business and customer keys are distinct (`apps/mobile/src/api.ts`, `apps/admin-mobile/src/api.ts`, both `session.ts` files).
- The portal dashboard and business live-order hook reject stale restaurant/request results; new order confirmation remains an explicit operator action. Preserve these protections when reducing polls.
- Service workers exclude API data. Customer navigation falls back to a public offline page, and the portal caches its offline page only. Never add customer records, receipt data or authenticated documents to these caches.
- Docker installs from the lockfile with lifecycle scripts disabled and starts the API as the unprivileged `node` user after volume-directory ownership setup. `.gitignore` and `.dockerignore` exclude private runtime data/reference source. These are useful safeguards, not proof that historical Git contents or deployed secrets were reviewed.

## Dependencies and test coverage

The API and print bridge rely largely on Node built-ins. Portal dependencies are React, React DOM and React Router, with Vite/plugin-react for builds. Native apps use Expo/React Native, SecureStore and purpose-specific location, image, audio, file or sharing libraries. Source references were found for the main declared native feature libraries; no dependency is declared unnecessary solely because it appears large or is absent from one screen. Different React versions in portal/native are separate runtime constraints, not automatically a defect.

The parent audit ran fresh validation: portal build passed (75 modules; JavaScript 470.81 kB / 136.85 kB gzip; CSS 79.76 kB / 16.24 kB gzip); both native typechecks passed; customer native tests passed 12/12 and business native tests 6/6; release packaging passed (126 JavaScript files, 24 required files). Root tests completed in 64.399 seconds with 231 passes and one failure out of 232, no skips. The failing `apps/api/test/finance-operations.test.js:70` was also reproduced in isolation: its fixture moves `created_at` to January 2020, expires the order, then expects a customer detail response. The implemented 90-day terminal-order visibility policy correctly hides that old order (`apps/api/src/customer-order-history.js:3-11`), so the test dereferences missing success data. This is a stale test fixture, not demonstrated failure of order expiry; update the fixture to fall outside the expiry interval but inside the history window, assert response status and retain a separate history-policy regression. The suite remains failing until that reviewed test correction is made. Dependency output is retained privately at `artifacts/audit-dependencies-2026-10-30.json`; see the main evidence report for interpretation.

Root tests are Node tests for API journeys, model/rendering helpers, printer simulation and local tooling. `apps/api/test/customer-journey-e2e.test.js:1-15` is an HTTP fixture journey; its name does not mean it drives a real browser or installed phone. No browser automation runner/config or React component interaction-testing dependency was found in tracked Cal-Eats files.

Required regression matrix before refactoring: customer browse/offer/modifier/basket/price-review/payment-return; owner/staff/admin authorization and restaurant switching; order confirmation/ETA/status changes; inbox/support unread state; duplicate click and lost-response recovery; unavailable API/slow API; logout/session expiry; service-worker update/offline/reconnect; keyboard/screen-reader/touch interaction; real Surface audio/printing; installed iOS/Android foreground/background transitions. Capture baseline screenshots at the existing viewport sizes and compare approved changes.

## Deployment, monitoring and recovery procedure

This is a proposed gated procedure, not an action performed in this audit.

1. Record the approved destination, source commit, image digest, database version, environment names, secret versions and responsible operator. Build and test in the separate test repository/staging environment. Verify all release gates, not only `release:check`.
2. Exercise the actual image with a fresh synthetic volume. Check mounted-directory permissions, health readiness, exact-origin cookies/requests, portal asset routing and graceful shutdown. Until the reviewed storage architecture changes, use a single writable SQLite instance; adding API replicas against the same file is not a scale plan.
3. Resolve FO-01/FO-02, make a consistent protected backup and prove restore to a different path/volume. Escrow matching keys separately. Record measured backup age, restore duration and reconciliation results; set RPO/RTO with the business from these observations, not assumed numbers.
4. On an approved deployment, take the pre-change recovery checkpoint, control incoming writes/worker execution and apply only reviewed forward-compatible migrations. The current startup auto-migration behaviour means rolling the image back does not roll the schema back.
5. Verify customer checkout, payment-state reconciliation, restaurant confirmation, one intentional print, service email, health and tenant isolation using approved test transactions. Observe error/latency/queue dashboards during the agreed window.
6. For rollback, disable the affected integration or roll back a compatible image first. A database restore can discard newly accepted orders/payments and reintroduce old jobs; require a reconciliation plan and explicit approval before a destructive restore. Preserve the failing state privately, restore to a separate environment, compare provider/order/print ledgers and switch only after review. Do not auto-replay unknown payment, email or print outcomes.

There is a health probe and application audit/job state, but no checked-in external monitoring/alert configuration or frontend telemetry collector. Add redacted request IDs, API latency/error rates, event-loop delay, database busy/transaction timing, queue age/retry/unknown counts, provider reconciliation lag, bridge last-seen/print outcome, disk space and backup age. Avoid logging passwords, tokens, message bodies, addresses or payment secrets. Define who receives an alert and who can replay a job before enabling an alerting system.

| Symptom | First checks and safe response |
| --- | --- |
| `/business/` unavailable | Confirm the portal was built for the exact source commit and copied into the image; inspect static-route/readiness logs. Do not reseed the database. |
| Hosted writes/sign-in rejected | Compare exact `CALAI_ORIGIN`, browser origin, host and proxy configuration. Retain strict origin/auth protections. |
| Native app cannot connect | Check its built API origin, HTTPS and account role; a device's localhost is the device itself. Check release-config guards before changing them. |
| Orders appear late | Compare server order timestamp, API latency, dashboard polling, SSE connectivity and device visibility; check unconfirmed queue and print bridge independently. |
| UI stays busy/stale | Inspect deadline and in-flight behaviour, especially FO-06/FO-07; refresh authoritative state before retrying an order/payment action. |
| Messaging unavailable after restore | Check key availability/version and retention policy without printing secret values. Restore credentials through the approved secret process. |
| Backup command fails in image | FO-02 explains absent scripts and path mismatch; do not substitute an unsafe live SQLite file copy. Use the reviewed backup path/tool. |
| Rollback still shows older/newer UI | Check deployed asset commit and service-worker lifecycle using a dedicated test client; preserve API data as network-only. |
