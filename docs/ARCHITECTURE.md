## Architecture
- Node.js 24 (installed 24.19.0), ESM JavaScript, npm workspaces, no downloaded runtime dependencies for this milestone.
- `apps/api`: local HTTP server, domain services, repository, migrations and tests. Node built-in SQLite, crypto and test runner. Explicit SQL migrations, parameterized queries, foreign keys and transactional writes.
- `apps/web`: public landing page and browser preview of the customer app. Business/admin sessions are directed to the business platform; customer ordering has no operational workspace entry.
- `apps/portal`: the single business tablet platform, including restaurant menu/photo/price/availability tools, orders, earnings and restricted administrator controls. One build and shared sign-in, with server-enforced roles and restaurant isolation.
- `packages/contracts`: shared roles, statuses, validation bounds and money rules. Define API shapes here and in API.md before frontend implementation.
- `data/calai-eats.sqlite`: ignored local database. Test databases use temporary directories and must not touch demo data.
- Default server: `127.0.0.1:4310`. Local mode rejects production environment and non-loopback binding. Explicit hosted-preview mode requires a normalized HTTPS public origin, Secure cookies and exact Origin on every write; it refuses known demo accounts and seed operations. Authentication throttles persist in SQLite. Initial admin creation is an empty-admin-only secret-input CLI. External providers remain disabled. API endpoints under `/api`; health at `/health/live`, `/health/ready`.

## Security and isolation
Customer registration and pending restaurant applications are separate validated routes; arbitrary role input is rejected. Admins are created by local fixtures or the empty-admin bootstrap CLI. Seed is idempotent, local-only, and uses documented demo credentials. Passwords use salted scrypt; session tokens are cryptographically random, hashes stored in DB, expiry enforced. HttpOnly SameSite=Strict cookies gain Secure in hosted preview. Writes validate exact configured Origin (missing Origin is permitted only in local mode), JSON content type, request size and CSRF protections. No CORS wildcard. Login/register throttles persist in SQLite, keyed by the direct socket identity; trusted proxy and multi-instance rate limiting remain future work. Logout revokes session. API errors never expose SQL, stack traces, hashes or tokens.

All restaurant access is checked through membership derived from the authenticated user, never trusted client ownership fields. Customer reads restricted to own orders; restaurant sees only its own orders/menu; admin has deliberate global read/approval permissions. Unknown/inaccessible objects use safe errors. Validate body shapes, types, lengths, integer prices/quantities and allowed state transitions. Persist audit/order events. Avoid HTML injection in UI and receipt output. Host/origin checks and restrictive browser headers protect loopback app.

## Data model and correctness
Tables: users, sessions, restaurants, restaurant_memberships, menu_items, orders, order_items, order_events, ledger_entries, schema_migrations (and idempotency data as needed). Use text UUID identifiers and ISO UTC timestamps. Approval states `pending`, `approved`, `rejected`. Roles `customer`, `restaurant`, `admin`. Orders snapshot item names/prices, restaurant name, currency and totals. Calculate prices exclusively from active DB menu records belonging to the approved restaurant. Never accept a client-computed total or commission.

All money is integer GBP pence, bounded safe integers. Commission is 700 basis points, rounded half up once per order subtotal. Example: 1999 pence => 140 pence. Ledger records recognition at acceptance exactly once, transactionally with order event/status. Refunds (when implemented) are compensating entries, never mutation/deletion of original financial records. Cash receivable represents commission owed by restaurant, not money collected by platform. Never misrepresent mock funds as settled.

For this journey, accepted mock-card orders carry `mock_captured` and an explicit mock commission entry; accepted cash orders carry `cash_due` and a separate commission receivable entry. Completing a cash order is the restaurant's explicit confirmation of collection and must be explained by the UI. No automatic cash settlement or platform payout is implied. A later refund milestone must distinguish simulated card refunds from manually returned cash and reverse commission exactly once. Tax, legal receipt requirements, live settlements and production accounting are out of scope until the missing product/market specification is supplied.

Collection path: placed -> accepted -> preparing -> ready -> completed. Delivery path: placed -> accepted -> preparing -> ready -> out_for_delivery -> completed. Both allow placed -> rejected. Customers cannot change restaurant status. Order POST requires a bounded Idempotency-Key scoped to customer; same key/same canonical request returns original order, same key/different payload yields 409. Do not duplicate order, ledger or events on retries.

### Required delivery behavior
Restaurants configure enabled delivery, an exact UK postcode outward-code allowlist (for example N1 and N2), nonnegative fixed deliveryFeeMinor and minDeliverySubtotalMinor. Public restaurant DTO exposes these settings. Customer supplies delivery address `{line1,line2?,city,postcode}` when choosing delivery; no address is accepted for collection. Normalize/validate postcode, compare full outward code (N1 must NOT match N10), require configured minimum subtotal and enabled delivery, and revalidate server-side at order placement. No geographic distance or provider verification claims. Seed demo delivery N1/N2, 250 pence, 1000 pence minimum, clearly documented. Snapshot delivery address, fee and totalMinor = subtotalMinor + deliveryFeeMinor; fee excluded from provisional 7% food commission. Receipts and all role views display fulfillment and total, with address only visible to authorized order participants/admin. Dispatcher/courier integration is mocked; restaurant advances delivery manually. Preserve financial/address snapshots after menu or delivery-setting changes. Add meaningful delivery eligibility, boundary, tampering, status-transition and receipt tests.
