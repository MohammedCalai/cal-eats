## Financial assumptions and records

Current food-only historical commissions remain unchanged. Add versioned configurable commission policy with explicit food-only and food-plus-delivery options. New development agreements default to food-plus-delivery at 700 basis points, locked for 24 months with explicit start/end dates; label this as a development assumption until commercial approval. Tax is merchant-supplied information, never invented or added automatically. Merchant-funded free items have zero payable value; paid discounts reduce the relevant base. Cal-Eats charges no other platform fees, and bears provider costs. Capture at restaurant acceptance, cancel failed/rejected authorizations; completion establishes settlement eligibility, subject to verified funds and specific holds.

Model order earnings, ledger adjustments, provider cost, pending/available balances, transfer and bank payout separately. Use an append-only balanced financial journal or equivalent reconciliable posting groups, with immutable operation keys. Never issue cash sales as bank payout funds. Cash commission is a receivable until a separately authorised collection succeeds. Keep legacy ledger reports compatible and avoid double counting. Store provider and simulation provenance on every financial operation.

Default provider is a deterministic local simulator with labelled outcomes, including failures and delayed confirmations. A separate Stripe **test-only** adapter may use dedicated test credentials; reject live mode/keys. No existing credentials are read or reused. Stripe hosted onboarding verifies capabilities/requirements; a return URL never completes onboarding. Candidate charge flow is separate charges/transfers. Refunds, transfer reversals and commission adjustments are distinct operations. One bank-payout scheduler: provider automatic weekly schedule, with local workers handling transfer eligibility and reconciliation. Never run a second automatic bank-payout job alongside it. Local simulator represents that provider behavior explicitly. No provider verification claim without actual sandbox evidence.

New owner API family `/api/restaurant/restaurants/:id/finance`: `summary?from&to`, `orders?cursor&from&to`, `payouts?cursor`, `payouts/:payoutId`, and `statement.csv?from&to`. ## Refund cases

`POST /api/refund-cases` takes `{orderId,reason,itemIds?,description}`; reasons `missing_items|incorrect_items|quality|non_delivery|other`. Ownership required; active duplicate order+issue conflicts and further evidence attaches to the existing case. Submission never moves money. `GET /api/refund-cases` and `GET /api/refund-cases/:id` return only caller-accessible cases. Evidence upload `POST /api/refund-cases/:id/evidence` uses the bounded image input `{mimeType,dataBase64}`; private media retrieval requires case access. Photos optional. Retention/deletion is configurable and recorded.

Statuses: submitted, under_review, awaiting_restaurant, awaiting_customer, approved, partially_approved, rejected, refund_processing, refunded, refund_failed. Case detail includes reference, reason/items/description, role-filtered evidence/messages, requested/approved amount, events, execution state and simulation/provider provenance. Internal notes and cross-restaurant customer history are admin-only. A second distinct order request in the same London calendar month sets an admin review flag. Discretionary goodwill approvals are limited to one per month by default, using a separate classification; never block a statutory remedy or automatically approve the first request.

New `/api/admin/refund-cases` list/detail supports review, request-information, ask-restaurant, internal-note, reopen and decision actions. `POST /api/admin/refund-cases/:id/decision` takes `{decision:'approve'|'partial'|'reject',amountMinor?,reason,remedy:'refund'|'goodwill'}` plus Idempotency-Key. Approval reserves refundable amount and queues execution; only confirmed success displays refunded. Existing direct admin refund routes must not bypass complaint approval for a linked case. A restaurant reply is evidence, not a veto. Owner `/api/restaurant/restaurants/:id/refund-cases` list/detail/reply only exposes its own cases. Keep customer remedies separate from recovery from restaurants or already-paid bank payouts. Cash decisions require named repayment responsibility/method and explicit confirmation evidence; prevent duplicate returns. Configurable response targets/reminders/escalation use durable jobs.

## Printers and devices

Owner `GET/POST /api/restaurant/restaurants/:id/printers`, `PATCH /.../printers/:printerId`, and `POST /.../printers/:printerId/pairing-code`. Pairing codes are expiring, single-use and hashed. `POST /api/devices/pair` with `{code,name}` returns a device ID and opaque token once. Device tokens are hashed, revocable and restaurant/printer-scoped; they never derive identity from MAC, IP or caller-provided restaurant IDs.

Authenticated device routes: `POST /api/devices/heartbeat`, `POST /api/devices/jobs/claim`, `POST /api/devices/jobs/:id/ack`. Claim returns `{job:null}` or `{job:{id,claimToken,leaseExpiresAt,attempt,receipt,manualReprint}}`. Ack takes `{claimToken,outcome:'printed'|'failed'|'uncertain',detail?}`. Claim/ack is atomic and replay-safe. Network ambiguity after bytes may have reached hardware becomes uncertain and requires explicit reprint, never automatic duplicate paper. New accepted orders enqueue once per configured printer after commit. Owner can request a labelled reprint and view failed/uncertain status; no physical-success claim from browser handoff.

Bridge default transport is a local file sink for simulation, with a persistent journal across restarts. Device/API/config/service/log identities are Cal-Eats-specific. Hardware transport requires explicit configuration, not inferred original settings. Reject original Calai API hosts and malformed receipt/job data. No installer downloads/runs arbitrary remote scripts, kills generic node/print processes, changes original services or installs startup tasks automatically during development.
