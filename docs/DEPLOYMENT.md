# Local operation and future deployment

The default local profile runs only on loopback HTTP. An explicit `CALAI_RUN_MODE=hosted-preview` profile now permits an HTTPS-facing preview with Secure cookies, strict Origin/Host validation, persistent authentication throttling and refusal of the known demo accounts. See [HOSTED_PREVIEW.md](HOSTED_PREVIEW.md) for the exact guard and initial-admin contract and [CONTAINER_PREVIEW.md](CONTAINER_PREVIEW.md) for future single-instance packaging. Nothing is deployed. GitHub, Expo and Railway operations remain deferred by the user. Native builds, real providers and production hardening remain further implementation and verification work.

## Local configuration
`CALAI_HOST=127.0.0.1`, `CALAI_PORT=4310`, `CALAI_ORIGIN=http://127.0.0.1:4310`, `CALAI_DB_PATH=data/calai-eats.sqlite`. Defaults work without environment variables. Set variables through the invoking environment; no secret file is required. Keep SQLite files, WAL files and future credentials out of Git. Do not put real customer information into the seeded local demo. Shut down cleanly before copying a database for a simple local backup.

## Provider boundaries
The default provider is a deterministic local simulator with no card data or external requests. A Stripe-test HTTP adapter and schema-v17 signed event/reconciliation boundary exist, but have only mocked local coverage and are not activated against Stripe. They do not make simulator orders provider-paid, and scheduled simulator payout batches are not bank-paid payouts. Cash states remain explicit simulated/manual bookkeeping. Delivery is configured postcode coverage, not a courier service. The separate print bridge defaults to a verified file sink; physical hardware is unverified. No SMS, real email, map or dispatch service is active.

## Before a separately authorized sandbox integration
Local recovery and email confirmation now use expiring, single-use tokens and a private mail sink. The UI labels simulated delivery explicitly. Connecting a real email provider requires independent delivery, sender-domain and recovery-flow verification; the local confirmation flag alone does not demonstrate ownership of a real address.

The current product context is Luton, UK, GBP and restaurant-owned drivers. Confirm commercial details in PENDING_DECISIONS.md, including delivery coverage and fees, commission base/timing, refund policy and taxes. Implement provider adapters, webhook verification, event replay protection, compensation/refund tests and reconciliation with sandbox credentials that belong only to Calai Eats. Never infer Stripe sandbox verification from a successful mock payment.

## Before a separately authorized production release
Validate the supplied HTTPS/Secure-cookie and Origin/Host controls in the chosen environment. Add managed secrets, trusted proxy identity and distributed throttling if scaling, verified external account emails, approved audit/retention rules, automated private backups with restore exercises, monitoring, migration recovery and a comprehensive payment/tenant security review. SQLite is currently restricted to one instance and a persistent writable volume; scaling requires a reviewed database architecture. Start from an empty database with an independently chosen administrator; do not copy the demo database. Verify accessibility, mobile installation and actual receipt obligations for the chosen market. Docker is unavailable on the current machine, so container build and platform volume permissions still require validation before hosting.

Provisioning billable services, live payments, DNS, GitHub pushes/Actions, Expo EAS and store submissions remain prohibited. The original Calai GitHub account/repository is permanently no-write. Future Cal-Eats publication must use a separately authorised account/repository whose destination remains TBD. These notes do not authorize deployment. See SOURCE_TEST_DISCOVERY_INCIDENT.md before repository-wide discovery.
