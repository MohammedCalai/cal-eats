# Phase B: local product operations contract

Implement after finance Phase A, preserving all earlier APIs. Independent frontend ownership remains apps/web. Local-only fictional restaurants. No live delivery fleet, banking, email, push, identity verification or production authentication claims.

## Restaurant profile and discovery
Restaurant DTO gains `profile:{description,cuisine,phone,address,collectionEnabled,cashEnabled,paused,busyMinutes,estimatedDeliveryMinutes,estimatedCollectionMinutes,openingHours,holidayDates}`, `acceptingOrders`, `closedReason`, `suspended` and `foodInformation:{verificationStatus,source,checkedAt}` (unverified default). `address` is text; `openingHours` is an array of `{day:0..6,open:"HH:MM",close:"HH:MM"}` (0 Sunday). Empty hours is CLOSED unless `alwaysOpen:true` is explicitly configured as local fixture behavior. Support overnight intervals, London timezone/DST and holiday closure by local date. Times are estimates, not driver tracking. Public DTO omits private business details.

`PATCH /api/restaurant/restaurants/:id/profile` accepts bounded profile fields plus optional name, `alwaysOpen`, and cuisine. Owner only; refuse unknown fields. Existing seeded demo locations migrate to explicit alwaysOpen and LU1/LU2 only if their legacy fixture values match exactly. Do not overwrite customized settings. `GET /api/restaurants?postcode=LU1%201AA&fulfillment=delivery|collection&q=...&cuisine=...` filters approved, nonsuspended restaurants by full outward code, fulfillment capability and case-insensitive search/cuisine. Expose closure/paused state to UI; checkout revalidates open/not paused, fulfillment, cash enabled, menu and fee/minimum. Keep customer platform fee zero.

`PATCH /api/admin/restaurants/:id/suspension` `{suspended,reason}` admin only, audit logged. Blocks new orders and acceptance when suspended, while existing accepted orders can finish. Unverified hygiene data never displayed as an official rating. Admin may record source/check date via a bounded food-information update if implemented.

## Applications and staff
`POST /api/auth/restaurant-register` `{name,email,password,restaurantName}` creates server-fixed restaurant role, pending restaurant and owner membership atomically after password hash, with session. Same auth protections as customer signup; never client-selected role. Restaurant cannot become publicly orderable merely by registering.

Memberships gain `permission:"owner"|"staff"`, existing memberships owner. `GET /api/restaurant/restaurants/:id/staff` owner only returns `{id,name,email,permission}` list. `POST .../staff` `{name,email,password}` creates a dedicated restaurant staff user/membership; reject an existing email rather than attaching arbitrary users. Hash before DB transaction. Staff can see their own restaurant/menu/orders/receipt and progress orders; cannot edit menu/profile/delivery, add staff, create new restaurants, see commission statement/contract or perform admin operations. Owner authorization enforced in backend. Public known demo credentials apply only to explicit seed fixtures.

## Menu and order detail
Menu create/patch gains `category`, `allergens:[string]`, `dietaryTags:[string]`, `modifierGroups:[{id,name,minSelections,maxSelections,options:[{id,name,priceMinor,available}]}]`. IDs are stable merchant-specified short strings, unique within groups/item; bound group/options counts, text lengths and positive modifier prices (zero allowed). min/max nonnegative integers, max <= options length; required options must be satisfiable. Variants can be represented by a required group with one selection. Merchant-maintained allergen text is explicit before checkout and on receipt. Demo sample allergen data is labelled fictional; no scraped or inferred food information.

Order item input gains optional `modifiers:[{groupId,optionIds:[string]}]`. Server checks all required groups, unknown/unavailable/duplicate options and min/max cardinality. Prices remain entirely server-owned. Snapshot selected modifier names/prices, base price, allergens and category, and preserve them after menu edits. Customer order body also allows bounded `customerPhone`, `deliveryInstructions`, `allergyNotes` (prominent in restaurant view/receipt). Authenticated name/email snapshots added as `customerName`/`customerEmail` only in authorized order DTOs. Reorder remains a client reconstruction into current menu with fresh choices, never replay historical totals or bypass required modifiers.

## Accounts and support
`GET /api/account`: `{id,name,email,role,phone}`. `PATCH /api/account` `{name?,phone?}`; no public role/email edits. `GET /api/account/export`: own sanitized profile/orders/support/deletion-requests only, never hashes/sessions/other tenants. `POST /api/account/deletion-requests` `{reason}` persists review request and audit; never silently deletes financial records. `GET /api/account/deletion-requests` own array. State explicit: requested, not erased.

`GET /api/support` own array; `POST /api/support` `{subject,message,orderId?}` validates order ownership/restaurant membership where linked. DTO `{id,userId,orderId,subject,message,status,createdAt,updatedAt}`. `GET /api/admin/support`: all cases. `PATCH /api/admin/support/:id` `{status:"open"|"resolved"}` audit logged. `GET /api/admin/deletion-requests` and `PATCH /api/admin/deletion-requests/:id` `{status:"under_review"|"resolved",note}` record administrative review only; resolution is not a claim of erasure.

## Local operational completeness
Expose persisted jobs/integration status/audit/financial CSV exports and support in admin. Notification adapter stores a local sink; UI shows connection and last refreshed status and a local notification test. Printer record distinguishes requested, browser opened and failure, and reprints; never physical success. Include an estimated margin calculator with user-entered processing/Connect/payout/refund/other costs in integer pence, labelled estimate; gross 7% is not net profit. No invented current provider prices.

Tests: checkout closure/overnight/DST/holiday/pause/cash disable, staff cross-tenant/admin denial, onboarding remains pending, required modifier/invalid selection/pricing/snapshot/receipt, export isolation, support/deletion authorization and audit. All prior financial and persistence tests must still pass. No new downloads/services needed.
