# In-app notifications and tailored offers — phase C

User instruction, 2026-10-24: notifications for specific orders, merchant customer views, tailored offers and analytics. User explicitly chose **offers only** for this phase; automatic ten-order rewards are deferred. All notifications remain inside the local app. No external email, SMS or device push is sent.

## Ownership and boundaries
Backend agent owns apps/api, packages/contracts and root scripts. Web agent owns apps/web. Existing API envelopes remain `{data: ...}`. All writes enforce the existing origin/auth policy. Merchant customer, campaign and analytics endpoints are owner-only; staff retain order notifications only. A merchant can target only customers with at least one completed order at that restaurant. Never expose other restaurants' history or private account/email/address data in the customer directory.

## Frozen routes and DTOs
- `GET /api/notifications` -> `{items: Notification[], unreadCount}`. Notification `{id,type,title,message,orderId?,offerId?,restaurantId?,createdAt,readAt}`. All roles receive only their own notifications. Persist new-order notifications to restaurant members and order-status notifications to the ordering customer, including expiry/rejection/refund. Unique recipient/event keys prevent duplicate notifications after retries.
- `PATCH /api/notifications/:id` body `{read:true}` marks only the authenticated recipient's notification; idempotent.
- `GET /api/restaurant/restaurants/:id/customers` -> array `{customerId,name,completedOrderCount,netSpendMinor,averageOrderMinor,lastOrderAt}`. Spend includes completed orders minus refunded totals; summaries and all source queries are tenant scoped. IDs are for targeting, not exposing global customer history.
- `GET /api/restaurant/restaurants/:id/offers` -> campaign array `{id,title,message,menuItemId,itemName,itemValueMinor,minSubtotalMinor,expiresAt,createdAt,recipientCount,openedCount,reservedCount,redeemedCount}`. Counts derive from persisted recipients and actual states, not estimates. Opened means offer viewed; redeemed means qualifying order completed. No claims about email delivery or gross revenue attribution.
- `POST /api/restaurant/restaurants/:id/offers`, required Idempotency-Key, body `{customerIds: string[],title,message,menuItemId,minSubtotalMinor,expiresInDays}`. 1–100 distinct eligible own customers, title 1–80, message 1–500, minSubtotalMinor integer 0–100000, expiry 1–90 days. Owner explicitly funds one free menu item for each recipient. Item must belong to merchant, available, and have no required modifiers. No percentage discounts or automatic rewards in this phase. Same key/body returns same campaign, changed body conflicts. Campaign + recipient grants + in-app notifications + audit are atomic.
- `GET /api/offers` -> authenticated customer's grants array `{id,campaignId,restaurantId,restaurantName,title,message,menuItemId,itemName,itemValueMinor,minSubtotalMinor,expiresAt,status,viewedAt}`. Status `available|reserved|redeemed|expired`; unavailable items may additionally make checkout reject with a useful error. Optional `restaurantId` filter accepted.
- `PATCH /api/offers/:id` body `{viewed:true}` marks only own grant viewed. This is also the open count source.

## Checkout and finance
Order POST accepts optional `offerId` (recipient grant ID), scoped to the authenticated customer and selected restaurant. Validate active approval, availability, expiry, minimum **paid food** subtotal and unused grant inside the same transaction as order creation. One grant per order; idempotent order retry cannot consume twice; concurrent orders cannot both reserve it. Free item is added by the server, quantity one, zero price, no paid extras. Client totals, free item IDs, prices and discount values are never trusted. Preserve item name/value and campaign terms in the order snapshot, exposed as `offer: {offerId,title,menuItemId,itemName,itemValueMinor}` and clearly labelled in receipts. Order items include the zero-price free item; use `isOfferItem:true` on that item for UI if supported.

Commission is 7% of paid food subtotal only; delivery fee and free item excluded. Existing delivery minimum uses paid food subtotal. These offers include a free item with the next order: at least one ordinary paid line and positive paid food subtotal are required, even when the offer's additional minimum is zero. No platform subsidy. Do not change ordinary order/refund behavior. On order rejection/expiry, release reserved offer; on full refund before completion release it because fulfillment is blocked. On completion mark redeemed; later refunds do not automatically create a second free-item entitlement. Expired released grants stay expired. Tests must cover cross-tenant/customer isolation, duplicate send, targeting eligibility, expiry/minimum/tampering, concurrent redemption, reject/expiry release, completed analytics and commission accuracy.

## UI
Inbox bell/count for all roles; readable notification list with mark-read and open-order/open-offer actions. Poll while signed in, stop/reset on logout, preserve typed forms. Customer Offers screen shows terms and available offers, marks viewed on deliberate open, selects an offer for checkout. Restaurant owner gets Customers & offers tab: customer history summaries, choose recipient(s), free menu item, minimum, expiry and message; send in-app and show campaign analytics. Keep labels explicit about local in-app delivery and merchant funding. Show saved, failed, empty and unavailable states. No actual external customer communication.


## Automatic basket and checkout offers — 30 October 2026

Customer `POST /api/orders/quote` accepts optional `autoApplyOffers: true`. It evaluates the signed-in customer's available, non-dismissed, active grants for the same restaurant and minimum spend, then applies one eligible exclusive promotion using server-owned prices and the existing consent, item, fulfilment and budget checks. The lowest actual payable total wins; a greater free-gift retail value breaks equal-total ties. Existing explicit `offerId` quoting remains compatible when automatic selection is not requested.

Evaluation is bounded to 100 newest active/minimum-eligible grants per restaurant/customer. The response includes `offerId` (or null), promotion/gift details and `autoOfferSelection` with `candidateLimit`, `candidatesChecked` and `truncated`. A truncated result is not an exhaustive best-offer guarantee. Quotes never reserve or redeem a grant.

Browser/native checkout wait for a complete delivery address (collection needs no address), refresh automatically on relevant edits and use bounded transient retries/foreground refresh. The final confirmation compares price and promotion/gift identity, including equal-price changes. Order creation sends the confirmed `offerId` and `expectedTotalMinor` through the existing idempotent flow; `autoApplyOffers` is not an order-creation parameter. The server rechecks eligibility at creation. Existing commission remains 7% of discounted food plus actual charged delivery under the current default; historical snapshots are preserved.
